# kava-business-platform-admin 项目宪法

## 核心原则

### 一、规范优先

每个功能必须从规范开始，遵循 Speckit 工作流程：

- **强制流程**：`/speckit.specify` → `/speckit.clarify` → `/speckit.plan` → `/speckit.tasks` → `/speckit.implement`
- **规范即契约**：spec.md 定义做什么(WHAT)和为什么(WHY)，plan.md 定义怎么做(HOW)
- **文档驱动**：在编写任何代码之前，必须有完整的规范文档
- **变更追溯**：任何需求变更必须先更新规范，再更新实现

**理由**：规范优先确保开发方向明确，减少返工，提高团队协作效率。

### 二、增量交付

每个用户故事必须独立可测试、可部署、可演示：

- **故事独立性**：每个用户故事(P1、P2、P3)必须能独立完成价值交付
- **MVP 优先**：先完成 P1 用户故事，验证后再进行 P2、P3
- **检查点验证**：每个故事完成后必须验证其独立功能
- **不破坏已有**：新故事不能破坏已完成故事的功能

**理由**：增量交付降低风险，尽早获得用户反馈，支持持续交付。

### 三、YAGNI 原则

只实现当前明确需要的功能，避免过度设计：

- **禁止过度抽象**：不为"可能需要"的功能创建抽象层
- **简单优先**：选择最简单的解决方案，而非最"完美"的方案
- **延迟决策**：在必须做出决策时再做决策，不提前预测
- **删除不用的代码**：无用的代码和抽象必须删除，不保留"以防万一"

**理由**：过度设计增加复杂度和维护成本，YAGNI 保持代码库精简和可维护。

## 开发工作流

### Speckit 流程

1. **需求阶段**：使用 `/speckit.specify` 创建功能规范
2. **澄清阶段**：使用 `/speckit.clarify` 解决规范歧义（可选但推荐）
3. **规划阶段**：使用 `/speckit.plan` 生成技术实现方案
4. **任务阶段**：使用 `/speckit.tasks` 生成可执行任务清单
5. **实现阶段**：使用 `/speckit.implement` 按任务执行开发

### 质量门禁

- 规范必须通过检查清单验证后才能进入规划阶段
- 计划必须完成 data-model 和 contracts 后才能生成任务
- 任务必须按优先级顺序执行（P1 → P2 → P3）
- 每个故事完成后必须独立测试验证

## 治理规范

- **宪法权威**：本宪法高于所有其他开发实践
- **修订流程**：修订需要文档记录、团队讨论，重大变更需要迁移计划
- **合规检查**：所有 PR/代码审查必须验证是否符合本宪法原则
- **复杂性证明**：任何违反 YAGNI 的复杂性必须有充分理由和文档说明
- **运行时指导**：开发过程中遇到冲突，参考本宪法优先
